## What happened compared to the previous commit? (threading crate: livelock in the shutdown, found by Miri)
- reported: the second Miri run (after the `GetLogicalProcessorInformationEx` fix, below) got stuck in `spawners::every_job_a_spawner_got_accepted_runs_even_if_the_pool_closes_meanwhile` and the question was whether there is an endless loop.
- answer: yes, but in the pool, not in the test. The test's loops are fine (a producer ends on `PoolClosed`; the backpressure spin ends because every accepted job runs). The endless part was the T2 shutdown protocol: `drop(pool)` set the shutdown flag and then waited for the workers, which only leave when they see the queue empty (`queued() == 0`); at the same time a `Spawner` kept being accepted from any thread until the pool had finished shutting down. A producer that adds jobs about as fast as the workers run them keeps the queue non-empty, so the workers never leave, `drop(pool)` never returns, the pool never closes, and the producer (which stops only on `PoolClosed`) never stops: a livelock. Native runs happened to pass because a producer is occasionally descheduled; Miri's deterministic scheduling does not give that luck.
- measured before the fix (a temporary test, release build): with one worker and jobs a little slower than the producer, `drop(pool)` took 788 ms and returned only because the experiment's own cap of 1.5 million jobs ended the producer (without a cap it would never return); with a faster job it ended in a few ms, but the producer's accepted-job count kept rising during `drop` (36 337 to 69 516 with four workers), which shows the dependency.
- fix: from the moment the shutdown begins, `Shared::submit` refuses (`PoolClosed`, task handed back) a job from any thread that is not running one of the pool's jobs. Workers' own spawns go to their own queue as before; a thread that is running a job of the pool still may spawn, because those jobs are part of the work the shutdown must finish (this keeps a chain of jobs that spawn jobs working on a pool with no workers, where the thread that shuts the pool down runs them). To know whether a thread is running a job of a pool, `worker.rs` keeps a per-thread stack of pool ids (`enter_job` guard, `is_running_job_of`), and every job the pool's code runs goes through `Shared::run_task` (workers, helping waiters, scope waits, the shutdown's own drain). Cost: one push and one pop on a thread-local `Vec` per job.
- behaviour change (T2 API): `Spawner::spawn` now returns `PoolClosed` as soon as the shutdown has begun, not only after it has finished, unless the caller is running one of the pool's jobs. `ThreadPool::spawn` is not affected (it needs `&self`, so the shutdown cannot have begun). The scope/join/parallel operations on a spawner already fell back to running on the calling thread. Docs of `Spawner`, `ThreadPool`, `ThreadingError::PoolClosed` and the book page say so.
- tests: the test that hung now runs under a watchdog (`within_patience`: the scenario runs on its own thread and a deadlock or livelock becomes a failure that names what did not finish, after 20 s, instead of a run that never ends) and closes the pool after a count of accepted jobs instead of after a sleep. Two new regression tests, `a_pool_shuts_down_even_while_another_thread_keeps_spawning` (a producer keeps spawning jobs that cost about ten times what spawning one costs, so the one worker can never empty the queue; the producer counts the jobs accepted *after* the test began to drop the pool and ends by a refusal with the fix, by a limit of 200 000 such jobs without it) and `a_spawner_refuses_other_threads_as_soon_as_the_shutdown_begins` (a gate keeps the only worker busy, so the pool cannot finish; the test thread must start to be refused while the pool is still shutting down). Three unit tests for the per-thread job tracking in `worker.rs`.
- mutation check (the new guard in `Shared::submit` replaced by `if false`): both new tests fail natively, with the messages "the producer went on and on after the shutdown began: it was not refused" and "the shutdown test did not finish within 20s: a deadlock or a livelock" (3 of 3 runs, and 4 of 4 runs in the `--cfg miri` configuration); with the guard they pass (15 of 15 runs in each configuration). Two false starts are worth knowing: my first version of the first test used a producer limit counted from the start, and the simulated-Miri run showed that the small scaled limit could be reached before the shutdown flag was set, so the test failed on correct code; and my second version used a job so cheap that the bug did not show natively (the mutation check passed the test, which proved the test useless) until the job was made ten times dearer than a spawn.
- counts: 44 unit (+3), 26 + 17 (+2) + 35 integration, 17 doc tests.

## What happened compared to the previous commit? (threading crate, T3: scoped jobs, join, parallel loops)
- added: `ThreadPool::scope` and `Scope` (`spawn`, `spawn_with_priority`): jobs that may borrow from the surrounding code; `ThreadPool::join(a, b)`; `parallel_for(range, f)`, `parallel_chunks(range, chunk_size, f)`, `parallel_for_each(slice, f)`, `parallel_for_each_mut(slice, f)`, `parallel_chunks_mut(slice, chunk_size, f)`. `Spawner` has the same seven operations (so a job can parallelize its own work); on a spawner whose pool has shut down they run on the calling thread alone. New modules: `scope.rs` (the only `unsafe` in the crate) and `parallel.rs` (safe code).
- decision: `scope` follows `std::thread::scope` (`'scope` invariant and higher-ranked, `'env: 'scope`). `Scope::spawn` returns nothing (like rayon's): results go back through what the job borrows, or through `join`. A job panic does not stop the other jobs; after all are done the scope re-raises the first one. If the body panics, the jobs are still waited for and the body's panic wins. Nothing is cancelled.
- decision: the one `unsafe` block is `mem::transmute` of `Box<dyn FnOnce() + Send + 'a>` to `'static` (`erase_lifetime`). Soundness rests on six invariants written at the top of `scope.rs`: every job owns a guard that counts it as pending; the job is declared before the guard so it drops first; `run_scope` waits for the count to reach 0 before it returns or unwinds (body in `catch_unwind`, abort guard around the wait); the counter is under a mutex (visibility); invariant higher-ranked lifetimes; panics are caught in the task so a worker never unwinds. The module is allowed `unsafe_code` with the reason spelled out, like `memory::bump`.
- decision: the waiting thread runs queued jobs until the scope is idle and yields (instead of blocking) while a push is in flight; it blocks on a condition variable only when nothing is queued and the remaining jobs are running elsewhere. `join` runs `a` on the caller and spawns `b`; because a job spawned on a worker goes into that worker's own queue and the worker takes its newest job back first, an unstolen `b` is run by the caller right after `a`.
- decision: the loops split by halves with `join`; boundaries fall on chunk boundaries, so `parallel_chunks(range, n, f)` sees exactly the chunks of `slice::chunks` whatever the schedule. `parallel_for*` without a chunk size aim for four chunks per thread (`workers + 1` threads); with no workers there is one chunk. Slices are split with `split_at` / `split_at_mut` (safe). A chunk size of 0 panics.

## What happened compared to the previous commit? (threading crate, T2: queues, stealing, priorities, spawners)
- decision: every worker gets a queue of its own, jobs from outside the pool wait in one shared queue, and idle workers steal. A search goes through the priorities from `High` to `Low` over all queues (strict priority), and inside a priority looks in the worker's own queue (newest first), then the shared queue (oldest first, so outside callers get first-in-first-out), then the other workers' queues (steal the oldest). Every queue has one lane per priority behind one `Mutex`; the locks are held only for the push or pop. Own safe code, no `crossbeam`, no `unsafe`.
- added: `JobPriority` (`Low`, `Normal`, `High`; `Normal` is the default), `ThreadPool::spawn_with_priority`, `Spawner` (`ThreadPool::spawner()`; `spawn`, `spawn_with_priority`; `Clone + Send + Sync + 'static`), `worker_index()`, and the error `ThreadingError::PoolClosed` (converts into `CoreError::InvalidState`). New modules: `queue.rs` (the only module that knows how jobs are stored: `push_external`, `push_local`, `pop`, `queued`, `close_if_empty`, so a lock-free version can replace it later), `sleep.rs`, `worker.rs`, `priority.rs`. `ThreadPool::spawn` is unchanged for callers (`Normal` priority).
- decision: a `Spawner` does not own or keep the pool alive, so a job that carries one can never be the last owner of its own pool. A job spawned from one of the pool's own workers goes into that worker's queue; every other job goes into the shared queue. While the pool drains at shutdown, jobs that running jobs spawn are accepted; `Spawner::spawn` returns `PoolClosed` only after the shutdown has finished. The shared queue closes only when it is seen empty under its own lock, so a job a spawner got accepted always runs, even when spawning races with the shutdown (tested with four producer threads).
- decision: idle workers sleep on a condition variable. A per-priority atomic counter is raised before a job is pushed and lowered after it is popped (it never wraps and never undercounts); the pusher then wakes a sleeper only if one exists (one atomic load otherwise), and a worker that is about to sleep announces itself and re-checks the counter under the lock, so a wake-up cannot be lost. A worker that sees a counter above zero but finds nothing yields and searches again (a push is in flight).
- decision: priorities are strict, so a steady stream of `High` jobs can starve `Low` ones; documented. A running job is never interrupted.
- tests: 34 unit, 26 (`tests/pool.rs`) and 15 (`tests/scheduling.rs`, new) integration and 4 doc tests. The new ones cover priority order in single-threaded mode, with a busy worker and for children; newest-first own queue; stealing from a blocked worker; wake-ups for sleeping workers (400 and 200 rounds); job trees that wait for their children at 0, 1, 2 and 4 workers; spawners during drain and after close; the close/spawn race.
- fixed: a latent flake in the T1 test `one_worker_runs_jobs_in_submission_order` (found by running the test binaries over and over: it failed once in 40 runs). The test thread called `wait`, which runs queued jobs itself, so two threads logged jobs concurrently and the log could come out of order. It now receives over a channel. This was a test bug, not a queue bug. A first version of the close/spawn race test also queued millions of jobs in its 30 ms (unbounded producers) and was killed by the sandbox; the producers are now bounded.
- changed: `docs/src/threading.md` (T2 items, queue rules, order guarantees, spawners, sleeping), crate docs, README row and introduction row. `Cargo.toml` and `Cargo.lock` are unchanged since T1.
- verified (Rust 1.91.1, Linux, sandbox toolchain): `cargo test -p threading` (debug and release), both integration test binaries run 150 times in a row in debug and 100 times in release without a failure, 15 times pinned to one CPU core (`taskset -c 0`) without a failure, `cargo clippy --workspace --all-features --all-targets -- -D warnings`, `cargo doc -p threading` with `RUSTDOCFLAGS=-D warnings`, `cargo fmt --all -- --check`. - added: `ThreadPool` (`new`, `spawn`, `run_pending`, `shutdown`, `worker_count`, `pending_jobs`), `PoolConfig` (`with_workers`, `with_name_prefix`, `with_thread_priority`, `validate`), `WorkerCount` (`Auto`, `Exact(n)`), `MAX_WORKERS` (1024), `DEFAULT_NAME_PREFIX` (`cv-worker`), `JobHandle<T>` (`is_done`, `wait`, `wait_catch`), `JobPanic` (`message`, `into_payload`), `ThreadingError` (`InvalidConfig`, `Spawn`; `#[non_exhaustive]`, converts into `CoreError`), `ThreadingResult`, and the re-export `ThreadPriority` from `platform::thread`. 15 unit tests, 26 integration tests (`tests/pool.rs`, including a block of single-threaded-mode tests) and 3 doc tests.
- decision: one FIFO queue behind one `Mutex` and a `Condvar`; the workers take from it in turn. No lock is held while job code runs, and a job runs inside `catch_unwind`, so a panic never reaches a worker: it is stored in the job's slot and re-raised by `wait` (or returned by `wait_catch`). Poisoned locks are taken back (`sync::lock`).
- decision: a thread that waits for a job runs queued jobs until its own is done. That is what keeps a job that waits for another job from deadlocking a one-worker pool, and what makes `Exact(0)` work. Consequence (found by a first version of the name tests): the waiting thread may run the very job it waits for, so a job cannot assume it runs on a worker thread; documented on `JobHandle` and in the book.
- decision: shutdown (drop or `shutdown()`) sets a flag, lets the workers drain the queue, joins them, and runs what is left on the calling thread (single-threaded mode). A pool whose last owner is a job on one of its own workers does not join that worker (it leaves when the job returns). A `JobHandle` may outlive the pool.
- decision: the thread priority is a request: when the OS refuses (Linux, raising a priority), the worker keeps the default and the failure is not reported. No `unsafe` code in this milestone; `Closure: Send + 'static` until scoped jobs (T3).

## What happened compared to the previous commit? (fix: immutable file mapping)

## What happened compared to the previous commit? (Phase 6.4, superseded by the entry above but kept for history)
- added (Phase 6.4): `renderer::FrameSync` (renderer/FrameSync.hpp) - the frame-level synchronization abstraction. `RenderDevice::CreateFrameSync()` builds it; `BeginFrame(swapchain)` waits for the in-flight slot's previous frame, acquires an image (100 ms timeout, so a hidden window can never block the GUI thread) and hands out a reset command buffer; `EndFrame(swapchain, frame)` submits and presents. Semaphores/fences stay inside the backend (acquire semaphore + fence + command buffer per in-flight slot, render-finished semaphore per swapchain image); a rebuilt swapchain is noticed by the next `BeginFrame()`, no extra call. Vulkan implementation in VulkanRenderDevice.cpp; `framesInFlight` is clamped to [1, 8].
- added (Phase 6.4): the editor render loop. `ViewportRenderer` owns a `FrameSync` (after the swapchain, so it dies first) and renders from a ~60 Hz timer on the GUI thread: a clear to a slowly cycling color, FPS in the status bar. The loop rests while the viewport is hidden or the window is minimized, and while the swapchain cannot be rebuilt yet (zero-sized viewport, failed rebuild - retried on the next resize and every 250 ms). `rebuildSwapchain(force)` no longer skips a rebuild just because the size is unchanged, so `OutOfDate` is always handled. Fatal errors (device lost, failed submit/present) stop rendering and show up in the status bar; recovering from them is not implemented.
- added: `Swapchain::Acquire(semaphore, timeoutNs)` and `SwapchainStatus::NotReady` (timeout expired, nothing acquired). `VK_ERROR_DEVICE_LOST` / `VK_ERROR_OUT_OF_*_MEMORY` now map to `RenderErrorCode::DeviceLost` / `OutOfMemory` for acquire, present, submit and begin/end instead of `Unknown`.
- added: validation as a test signal. `renderer::ValidationErrorCount()` (renderer/Diagnostics.hpp) counts validation-layer errors, `RenderDevice::IsValidationEnabled()` says whether the layer is running, `RENDERER_FORCE_VALIDATION` (CMake option) enables the layer in every build type.
